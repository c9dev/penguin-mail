# Penguin Mail

Terms the code and its docs use for Gmail mail. The `domain` crate holds the code for each.

## Glossary

**System label**: a label Gmail defines, with the same id in every account, such as `INBOX`, `SPAM`, `UNREAD`, and the category labels. `mailrs_gmail::labels` names them and maps each to a role, a keyword or a category; only the Google adapter and the Gmail fake read them. _Avoid_: system folder.

**User label**: a label the account owner made, with an id like `Label_12` that only that account knows. _Avoid_: custom label, tag.

**Category label**: one of Gmail's `CATEGORY_*` labels, which Gmail puts on inbox mail to sort it. The store keeps each as a category under the same name (`mailrs_domain::category::SOCIAL` and the rest), since Gmail is the only provider with categories. _Avoid_: tab, category.

**Category**: a slice of the inbox that Penguin Mail shows: All, Primary, Updates, Promotions, or Social over a Gmail account, and Focused or Other over a Microsoft account's inbox (`Category::FOCUS`). Each one is defined by the category labels a thread has or lacks. Primary is mail with no category label but Personal, and Social includes Forums. _Avoid_: tab, inbox type.

**Folder**: Archive, Junk, Trash, or All Mail. Archive is the received mail outside the inbox, which Gmail has no label for. The local store does not keep this mail, so the app lists a folder with a query tree, which Gmail receives as a search, and checks a message's labels to see if it still belongs there. _Avoid_: mailbox, spam folder.

**Target**: what a mail action applies to: a thread, or one message of it when the list shows messages instead of conversations. `mailrs_domain::Target`. _Avoid_: selection, item.

**Reach**: what a button or key pressed in one conversation view acts on: its targets, what they carry (unread, flagged, muted), and the mailbox they were picked from. In the main window several selected rows win over the open conversation; a conversation in a window of its own reaches only itself, in the mailbox it was opened from. `ui::window::reach::Reach`, built by `MainWindow::reach(view)`. _Avoid_: scope, selection.

**Message menu**: the menu a right click, the Menu key or Shift+F10 opens inside one message of an open conversation, every item of which changes that message alone rather than the thread around it: reply, archive, trash, mark, flag, label, export, copy the sender's address. `ui::window::message_menu::groups` decides which items a message gets from its own marks and the mailbox on screen, leaving out what would do nothing there; each item is a `win.message-*` action carrying the message id, so the change goes on the undo stack like any other. The page asks for it through the `mailrs:menu/` link the conversation view intercepts. It differs from a Reach, which is what the header buttons act on. _Avoid_: context menu, popup menu, per-message actions.

**Web view**: one page the app draws from HTML it wrote itself: the open conversation, the composer's Preview, a forwarded message under the editor. `mailrs::web::WebView`, with two kinds: `reading` runs the app's own scripts and answers the `mailrs-cid` scheme for inline pictures, and `sealed` runs no script and opens a web link in the browser. On Linux it is WebKitGTK's widget; on macOS, where WebKitGTK does not exist, it is a WKWebView laid over an empty GTK widget that holds its place in the window. Callers never name the engine. The hidden page that reads an unsubscribe form is a `Browser` of its own. _Avoid_: webview (for the type), page (which is a listing's), browser.

**Shortcut**: one line of the Keyboard Shortcuts dialog and the keys behind it, each naming the action it activates and the windows it works in: the main window, a conversation in a window of its own, both, or the composer. `ui::window::shortcuts::SHORTCUTS` builds both windows' key controllers and the dialog, so a key cannot work without the dialog listing it. A letter key, such as `e` or `#`, works only in the main window and gives way while you type in a text field. _Avoid_: accelerator, hotkey, keybinding.

**Mail action**: a change a person or the assistant makes to targets, such as archive, flag in a colour, remind at a time, or label by name. `mailrs_sync::MailActions` runs each one for the window and the assistant alike, carries on past a failed target, and reports each failure in its `Outcome`. _Avoid_: command, operation.

**Muted**: a thread carrying the `$muted` keyword, which Gmail keeps as its `MUTE` label. Muting is the keyword plus one archive, and unmuting drops the keyword and puts the thread back. Gmail's own filters archive whatever arrives on such a thread, even while Penguin Mail is closed. No other server has such a filter, and Outlook stores no `$muted`, so on Outlook, IMAP and POP3 accounts the engine files each reply itself as the feed brings it in: marked read, marked muted and moved to the Archive, before the window or a notification hears of it. That runs only while Penguin Mail runs; a reply that arrived while it was closed is filed at the next look, if it is still unread in the Inbox. A muted thread's reply raises no notification on any account. `mailrs_sync::TriageAction::Mute`, behind `MailAction::Mute`; `MailCapabilities::files_muted_replies` says which servers file replies themselves. The Muted mailbox lists these threads and a row marks them. _Avoid_: ignore, silence, snooze.

**Undo Send pill**: the pill at the foot of the mail sidebar while messages wait out their Undo Send delay, counting down the longest wait; a click calls back the newest message, which opens again in a composer. While the sidebar is collapsed or hidden, one toast stands in for it with the same Undo. `mailrs::ui::window::undo_send::Waiting`. _Avoid_: snackbar, banner.

**Undo**: the stack of recorded mail actions that Ctrl+Z or a toast's Undo button reverses, newest first. Each press takes one off and reverses what that action changed on each message, taking off what each message gained and putting back what it lost, as the change set reported it, so a message it found already read or archived stays that way. It also puts back earlier flag colours, earlier reminders, and dismissed follow-ups, and the toast names what it took back, a label or folder by the name the person gave it rather than the server's id. The stack holds twenty actions and lasts as long as the run: mail actions are already applied at Gmail, so one that outlived the process would offer to reverse what the server has long since moved on from. A target that has left the folder the action put it in is left there, which is why undoing an archive cannot pull a conversation back out of the trash; erased mail and a signed-out account take their entries with them. The window and the assistant share it. _Avoid_: history, revert.

**Aftermath**: what a mail action leaves stale in the window once it has run: rows to take out at once, a Gmail folder to prune or search again, the counts, the flag colour on open conversations, the Remind Me and Follow Up lists. `ui::window::aftermath::Aftermath::of` decides it from the cause (an action, an undo, or erasing) and the mailbox on screen, and `MainWindow::after_mail` carries it out for the window's buttons, Undo, Delete Forever, the assistant and the notification buttons alike. When an action takes mail out of the list, the window moves on before Gmail answers, by the one rule in `aftermath::leaves` and `MainWindow::move_on`: the next row opens, the conversation pane hides when no row is left, and a conversation in a window of its own closes. It differs from a settings change's effect and from the open thread's stale, which cover other causes. _Avoid_: refresh, side effect, effect.

**Press**: one use of a mail button, a key, a menu item or a drop on a sidebar mailbox, and the plan it comes to: the targets, the mail action and whether Undo keeps it, whether the window moves on first, the question before erasing, the toast's words, or what Delete calls off in Send Later and the Outbox. `ui::window::press::plan` reads the reach, the mailbox and whether the press covers what is shown, rows carried by a drag, or one message, and `press::carry_out` makes the plan happen through `PressEffects`, which the window stands behind and the tests fake. `press::trash_words` words the Delete button from the same table in each mailbox. _Avoid_: click, command, handler.

**Favorites**: the first section of the mail sidebar: All Inboxes, VIPs, Flagged with a row per flag colour in use, and Follow Up. The unified mailboxes that follow sit under Mailboxes, and each account's own under Accounts. `mailrs::ui::sidebar::sections::LAYOUT`. _Avoid_: pinned, starred mailboxes.

**Mailbox**: one choice in the sidebar, and what the thread list then shows: a standard mailbox in one account or across all, a person's label, a mail set with no row of its own that the assistant asks for by name, a folder, a search, a smart mailbox, a flag colour, VIP mail, Follow Up, Remind Me, Send Later, or the Outbox. `mailrs_sync::Mailbox`. _Avoid_: view, source, box.

**Standard mailbox**: Inbox, Flagged, Sent, Drafts or Muted, the five mailboxes the sidebar shows for all accounts together and for each one. `mailrs_sync::mailbox::Standard`; each lists one mail set: the inbox role, the `$flagged` keyword, the sent role, the drafts role, the `$muted` keyword. _Avoid_: system label, special folder.

**Queued message**: a message waiting to go out, kept on this computer with the bytes it will be sent from, what the composer needs to reopen it, the tries already behind it, and the time of the next one. `mailrs_store::outbox::Queued`, sent by `mailrs_sync::Outbox`. One table holds both kinds, because both are a message waiting: a Send Later message, whose hour has not come and whose bytes Gmail holds as a draft, and one that hit a problem on the way out. The recorded problem is what tells the two apart and decides which mailbox lists the message. Whoever sends one first takes it with `mailrs_store::outbox::claim`, so the Outbox window's Send Now and the pass that sends what is due never both send it; a claim lapses after ten minutes, for a run that died mid-send. A message tried before is looked for in Sent by its `Message-ID` before it goes again, since the try whose answer was lost may have reached Gmail. _Avoid_: pending message, spool entry, draft.

**Outbox**: the mailbox listing the queued messages with a problem against them, each row saying why the message has not gone and when the next try is. It stays in the sidebar when empty, so a person can look before anything goes wrong. The wait between tries doubles from half a minute to half an hour, the network coming back cuts it short, and after about a day of tries the outbox stops and leaves the message to the person, as it does at once for a failure nothing would fix. A message inside its Undo Send window is not here yet, since nothing is stored until that delay runs out. _Avoid_: queue, spool, pending.

**Mailbox on screen**: the mailbox the main window lists, the one a search goes back to when it closes, the inbox category, and the list feed that loads its rows. `ui::window::on_screen::OnScreen`. The sidebar, the search bar, a notification, a deleted label and a settings change each make one transition on it, and every transition answers with a `Redraw` naming what it left stale, such as the selection, the title, the buttons that hang on the mailbox, and a first page to list, which `MainWindow::redraw` carries out. A conversation in a window of its own keeps the mailbox it was opened from instead. _Avoid_: current mailbox, view state, navigation.

**Smart mailbox**: conditions saved in Preferences that become a query tree, such as "from Ann" and "newer than 7 days". Gmail receives the tree as a search. `mailrs_domain::SmartMailbox`. _Avoid_: saved search, filter.

**Listing**: one page of a mailbox, with its rows, its unread count, the title and subtitle the header shows, and what an empty list should say. `mailrs_sync::Mailboxes` produces it for the window and the assistant alike, so only it knows which mailboxes the store answers and which Gmail does. _Avoid_: result, page, query.

**View**: the settings that change what a mailbox lists: conversation grouping, the inbox category on screen, whether Follow Up is on, the clock, and a row limit. `mailrs_sync::View`. _Avoid_: options, config, filter.

**List feed**: what the thread list loads next, and which answers to that loading still count. It hands out the first page of the mailbox on screen, the next page once the reader scrolls to the end, and one refresh for a burst of change events, which re-reads the named threads, lists the mailbox again, or prunes a folder. `mailrs::ui::list_feed::ListFeed`. Every answer passes through it on its way to the window, and it drops the ones for a mailbox that has since left the screen. _Avoid_: loader, pager, generation.

**Settings change**: one named change to the preferences, such as the text size, an account's signature, or a VIP. `mailrs::settings::Change`. Preferences, the keyboard shortcuts, and the assistant all make the same change the same way, so the same input lands the same way whichever one asks. _Avoid_: patch, setting update.

**Effect**: the part of the window a settings change leaves stale: the list's shape, the sidebar's accounts, row colours, a smart mailbox's conditions, the VIP marks, Follow Up, the inbox categories, the assistant's connection and model, the text size, or light and dark. `mailrs::settings::Effect`. Applying a change reports its effects, the window redoes one part per effect, and a change with no effects saves the file and stops. The effects also carry what a change asks of the address books, read through `Effects::address_books`: switching an account's contacts on reads them, and switching them off deletes that account's, whichever caller made the change. _Avoid_: signal, notification.

**Account settings**: what Gmail keeps for one account and Penguin Mail changes: the automatic reply, the rules, blocked senders, and hidden addresses. `mailrs_sync::AccountSettings` makes each change for the dialogs and the assistant alike. Preferences, which live in the app's own settings file, are something else. _Avoid_: preferences, options, Gmail config.

**Automatic reply**: what Gmail sends back while the account owner is away, with the days it runs between. `mailrs_sync::AutomaticReply` names the first and last day; Gmail stores an end it stops before, and only `AccountSettings` converts between the two. _Avoid_: vacation, out of office, auto-responder.

**Rule**: one server rule: which mail it matches, and the mail sets it adds that mail to or takes it out of as it arrives (out of the inbox role skips the inbox, out of unread marks it read, into the trash role deletes). `mailrs_domain::Filter`; for Gmail each is a Gmail filter, and `mailrs_gmail::model::GmailFilter` holds Gmail's label ids on the wire. The Rules dialog, Block Sender, Categorize Sender, and Hide My Email all make rules. Gmail cannot change a filter, so editing a rule makes the new one first and then deletes the old one, `AccountSettings::replace_rule`; when that delete fails, both run and the dialog says so. A rule the server holds in a shape `Filter` cannot say is listed read-only (`Filter::read_only`): the dialog shows it with a line saying so and never rewrites or deletes it. _Avoid_: filter (except for Gmail's own), automation.

**Local rules**: rules for an account whose server runs none, kept on this computer in `local_rules` and run by Penguin Mail over new Inbox mail while it is open, through the same mail actions the window uses, so they queue and sync like any other change. They stay off the undo stack, so Undo takes back what the person did last. Mail that arrived while the app was closed runs through them once at the next start, oldest first; `accounts.rules_ran_until` and `local_rules_ran` see to the once. `mailrs_sync::rules::RulesEngine`, served to the Rules dialog by `mailrs_sync::services::LocalRules`. _Avoid_: client-side filters, local filters.

**POP3 account**: an account whose incoming server speaks POP3, which holds one list of messages and nothing else. Penguin Mail downloads that list into the account's own mailboxes in the store, which is the only copy of its mail, and sends through SMTP. Its rules are Local rules; its calendar and contacts come from CalDAV and CardDAV servers found for it. `Provider::Pop3`, served by `mailrs_sync::services::Pop3`. _Avoid_: offline account, download account.

**Local mailbox**: a mailbox that exists only in the store, as a POP3 account's Inbox, Sent, Drafts, Trash, Junk, Archive and the folders a person makes. A move or a flag is complete once the store has it; nothing goes to a server (`MailCapabilities::local_mailboxes`). Rules for such an account are Local rules. _Avoid_: local folder, offline folder.

**UIDL**: the name a POP3 server gives one message, which stays the same across sessions while the message numbers do not (RFC 1939). `pop3_seen` keeps each UIDL an account downloaded until the server stops listing it, so nothing downloads twice, with the store id of the message it brought. A row whose removal a clean QUIT confirmed no longer counts as downloaded: the server lists that UIDL again only for new mail. That id is `pop3/<uidl>`, or `pop3/<uidl>/<n>` when an older message holds it: a server may give a UIDL to a new message once the old one has left it. _Avoid_: message number, POP3 id.

**Removal setting**: what a POP3 account does with mail on the server once it is here: Leave on Server (the default), Remove After Downloading, or Remove After {n} Days. Removal sends `DELE` and takes effect at a clean `QUIT`; the copy here stays either way. Add Account sets it in Server Settings, and signing in again changes it. `mailrs_domain::RemoveSetting`, in `accounts.pop3_remove`. _Avoid_: delete from server, keep on server.

**Sieve script**: the one script, `penguin-mail`, that Penguin Mail keeps on a server that speaks ManageSieve, holding an account's rules and its automatic reply as blocks the app wrote, each under a comment naming the rule. A block someone edited by hand, or wrote there before, stays in the script and shows read-only as a rule written elsewhere. A script the person already ran is included into it where the server can (`include :personal`), and otherwise replaced only after the person says yes. `mailrs_sieve::script`; `mailrs_sync::services::SieveRules` serves it. _Avoid_: filter script, server filters.

**Hidden address**: one plus address from Hide My Email, such as `dana+kite.fern482@gmail.com`, with the rules behind it. One rule gives its mail the Hide My Email label; a second trashes that mail while the address is off. `mailrs_sync::HiddenAddress` holds the address, its note and the two rule ids; `AccountSettings` makes one and changes it, and the app keeps the list in its settings file. _Avoid_: masked address, burner.

**Built-in client**: the Google OAuth client compiled into a release build from `PENGUIN_MAIL_GOOGLE_CLIENT_ID` and `PENGUIN_MAIL_GOOGLE_CLIENT_SECRET`. Every new sign-in uses it. `mailrs_gmail::built_in_client`, recorded as `SignInClient::BuiltIn`. Microsoft has its own: a public client with no secret, compiled in from `PENGUIN_MAIL_MICROSOFT_CLIENT_ID`, which the release workflow fills from the `MICROSOFT_CLIENT_ID` secret; `mailrs_graph::built_in_client`. A Microsoft account's refresh token lives in the keyring under `penguin-mail-microsoft`, keyed by account id, and each one Microsoft rotates replaces it. _Avoid_: app key, default client.

**Account secrets**: where each kind of account keeps what signs it in. A Google account's refresh token sits in the keyring under `mailrs`, keyed by address; an IMAP or POP3 account's password under `penguin-mail-imap` and a Microsoft account's refresh token under `penguin-mail-microsoft`, both keyed by account id. `mailrs_sync::passwords::Secrets` holds the three stores, from the keyring or, for the demo and tests, from memory, and `Secrets::forget` deletes an account's secret from the store its provider uses. `mailrs_sync::Connector` adds the store, the settings and the build's clients, and its `connect` gives an account's services or says it needs a new sign-in (`Connected::NeedsSignIn`, with what it `Lacks`: the client or the secret). The app and the CLI start and remove every account through these. _Avoid_: credentials, keys.

**Browser sign-in**: signing an account in on its provider's own page: Google's consent or Microsoft's sign-in. `mailrs_sync::sign_in::Browser::of` says which one an account's provider uses, `None` for IMAP and POP3, which sign in again through the Add Account form. `mailrs_sync::sign_in::in_browser` runs it, refuses another address when the `Wanted` address is `Only` one, then keeps the account and its token and builds its services. _Avoid_: OAuth flow, consent flow.

**Own client**: a Google OAuth client a person made in their own Google Cloud project and pasted into the old setup page, kept in `config.toml`. Accounts added that way keep it until they sign in again. `SignInClient::Own`. _Avoid_: custom client, user client.

**Settings permission**: the access an account grants so Penguin Mail may read and change its account settings: Gmail's `gmail.settings.basic` for a Google account, `MailboxSettings.ReadWrite` (rules, Focused Inbox and the automatic reply) for a Microsoft one. It is asked for at sign-in along with every other scope in one consent. A person may leave it unticked; without it every `AccountSettings` call answers `Permitted::NeedsPermission`, and the caller offers Grant Access rather than showing an error. _Avoid_: scope, consent.

**Delete permission**: the access an account grants so Penguin Mail may erase mail: Gmail's full access for a Google account, `Mail.ReadWrite` for a Microsoft one. It is asked for at sign-in along with every other scope. A person may leave it unticked, and until it is granted `MailActions::erase` answers `Permitted::NeedsPermission` and changes nothing. _Avoid_: scope, full access.

**Permission prompt**: the Grant Access question that follows every `Permitted::NeedsPermission`, in the window or from an assistant tool, whether the scope was never asked for or the person unticked it on the provider's screen. Its words name the account's provider: Microsoft and Outlook for a Microsoft account, Google and Gmail otherwise (`mailrs::permission`). `mailrs::permission::Permission` names the settings, delete, contacts, contact change, calendar or calendar management permission, and its table holds each one's heading and body; sign-in asks for every scope in one consent, so nothing here picks scopes one at a time. The `Occasion` sets how often it asks: `Needed` when something stopped for want of the permission, each time; `Offer` when something worked without it and the permission would have done more, once per account a run. `MainWindow::ask_permission` shows it and runs consent on a yes. _Avoid_: consent dialog, access request.

**Tool call**: one thing the assistant asks the app to do, by name and with JSON: list a mailbox, organize mail, change a setting. Each mail tool is one entry in `mailrs::assistant::run::catalog`: its name, the label the pane shows, its JSON Schema, and its handler in `mailrs::assistant::run`, which either answers at once or plans a change and names the question to ask before making it. The mail tools reach the model as the source `mail`, beside web search, MCP servers and skills. The tools change mail through the same `MailActions` and `AccountSettings` the window uses, so the assistant cannot do anything the user could not. _Avoid_: function call, command, action.

**MCP server**: a program or web service the owner adds on the AI page to give the assistant more tools. `mailrs::assistant::sources::mcp` offers each enabled one as the source `mcp:<name>`, with its tools named `<name>__<tool>`, and `mailrs_ai::mcp::McpClient` speaks the protocol to it. The registry there starts a server on the first turn that needs it, keeps it for later turns, and stops it when the settings drop it or the app quits. _Avoid_: plugin, connector, extension.

**AI feature**: something in the app that sends words to a model: the assistant and translation today. `mailrs::settings::Feature`, one row each under Used For on the AI page. Each one uses a model of its own or follows the assistant's, and `mailrs::assistant::model_for` is the one way to a model, so every caller names the feature it is working for. _Avoid_: AI function, capability, skill.

**AI language**: the language of assistant answers, summaries and translations, selected on the AI page independently of the interface and model. `mailrs::settings::AiSettings::language` holds its name; empty follows the interface's active catalogue. A direct request for another language takes precedence, and email replies and drafts prefer the language of the correspondence. _Avoid_: locale (which controls the interface), system prompt (which carries this preference to the model).

**Connection**: a place a model runs, set up once on the AI page: a local server with OpenAI's API, the Anthropic API, or a Claude subscription through Claude Code. `mailrs::settings::AiProvider`, whose `Off` stands for none. Addresses and commands live in the settings and keys in the keyring, so two features on one connection share them. _Avoid_: provider (in wording the user reads), backend, endpoint.

**Search engine**: where a local model's `web_search` sends its query: the Brave Search API with a key from the keyring, or a SearXNG server asked for JSON. `mailrs::assistant::sources::web::SearchEngine`, chosen under Web Search on the AI page. Claude never uses one: through the API or Claude Code it searches with Anthropic's own tools, and the web source offers it nothing, so it never sees two searches. _Avoid_: engine (which names gpg and gpgsm), search provider.
**Turn**: one question to the assistant and everything the model did to answer it, in the order it arrived: what it thought, each tool call with its input and result, and the reply. `mailrs::assistant::turn::Turn` takes the model's events and says which step each one changed, and the pane draws a folded row per thinking step and tool call. While the turn runs its phase says what the model is doing now: waiting for the model, thinking, running a tool, waiting for the person to allow one, or writing. _Avoid_: exchange, message, round (which is one request to the model, and a turn can take several).

**Chat history**: what a chat sends back to the model each round: the turns so far, oldest first, and the one under way. `mailrs_ai`'s `history::History`, which the Anthropic and local-server providers both render. A turn that fails or that Stop cut short is taken back whole, question and all, and old turns leave the front whole when the chat outgrows its budget, so the model never reads a tool result without the call it answers. It also names where the cache breakpoint goes, on the latest message from the user's side. _Avoid_: context, transcript, conversation (which is the whole chat object).

**Skill**: a folder of instructions for one kind of task, with a `SKILL.md` whose front matter gives a name and a description, found in Penguin Mail's skills folder or Claude Code's. `mailrs::assistant::sources::skills::Skill`, whose id is where it came from and its folder's name, such as `claude-code/pdf`. Each is off until the person turns it on; the system prompt lists the ones that are on, and the model reads the rest with `use_skill`. _Avoid_: plugin, extension, AI feature (which is something in the app that sends words to a model).

**Sandbox**: where a skill's commands run: bubblewrap with the system's programs read-only, the skill's folder at `/skill`, a scratch folder at `/work` that lasts as long as the chat, no home folder, and no network unless the skill is allowed one. `mailrs::assistant::sources::skills::sandbox`. The shell source asks the person before each command. _Avoid_: container, jail (in wording the user reads), VM.

**Desk**: the port a module reads the window through. The assistant's tools read the preferences, the accounts and their labels, the view, and what is on screen, meaning the mailbox, the open conversation, and the selected rows: `mailrs::assistant::run::Desk`. The engine run reads which engines this computer has, the protected messages it claims, and whether that thread is still on screen: `mailrs::protection::run::Desk`. The thread run reads the conversation on screen, the reader's settings that shape it, and what the page draws for a translation: `mailrs::open_thread::run::Desk`. The calendar run reads the accounts, the pages and their ranges, and what each part of the calendar page shows now: `mailrs::ui::calendar::run::Desk`. Every method gives back plain data, so a test fills one in without a widget. _Avoid_: context, state, session.

**Effect port**: the port a module changes the window through. The assistant's tools approve, open, compose, send, copy, ask for the settings permission, and the rest: `mailrs::assistant::run::Effects`. The engine run fetches the message as it was sent, asks gpg or gpgsm about it, and puts the answer above it: `mailrs::protection::run::Effects`. The thread run reads the store and Gmail for the thread, its bodies, pictures, invitation and flag colour, asks the model for a translation, and makes the named changes on the conversation view: `mailrs::open_thread::run::Effects`. The calendar run reads the local copy and draws pages, lists, the sidebar and popovers: `mailrs::ui::calendar::run::Effects`. The window is one adapter behind each and the tests are another, so all four run with no GTK. Not to be confused with a settings `Effect`, which names a part of the window a preference left stale. _Avoid_: side effect, callback, handler.

**In-memory Gmail**: `mailrs_sync::fake::FakeGmail`, one account's mailbox held in memory behind the same `GmailApi` seam as the real client. It answers Gmail's search language, keeps a history log, and takes writes. It also holds the account's calendars and their events, answering the calendar list, a calendar's change feed and its writes the way the real Calendar API does, with a log of what changed for a test to read directly. A test can withhold an OAuth scope so calls that need it answer `MissingScope`, switch the Calendar API off, and pin the clock `newer_than` counts from. Sync's tests, the assistant's tool tests, and `penguin-mail --demo` all run on it, so there is one fake to keep honest rather than two; sync ships it under the `fake` feature so only the app and the tests carry it. `mailrs_sync::fake::fill_store` fills a new account's store from it through sync's own bootstrap and backfill, which is how the demo and the assistant's tests get their mail into the store. _Avoid_: mock, stub, demo API.

**Rich body**: the composer's message while it is being written as rich text: lines with a kind, each carrying runs of styled words. `mailrs::richtext::RichBody`. It becomes the HTML part of the message, the plain text part beside it, and the Markdown a writer who prefers marks sees, and it reads Markdown back in, which is how a reply's quote and the assistant's drafts arrive. _Avoid_: document, rich text, formatted body.

**Stray Markdown**: Markdown marks, such as `# `, `- ` or `**`, sitting in a rich body as plain characters because someone typed them or pasted plain text. `mailrs::stray_markdown` says whether text reads as Markdown, strictly enough that a letter never does, and which of the writer's plain lines to replace with styled ones; the quoted history, the signature and lines already styled stay as they are. The composer pastes Markdown styled and offers the bar that formats what is left. _Avoid_: raw Markdown, unformatted Markdown.

**Send gate**: what stands between a finished message and sending it, one check at a time: a message that cannot go is refused, then a message meant to go out encrypted that cannot be is asked about, then a promised file that is missing. `mailrs::compose::gate` names the next step, and the composer asks what it says to ask until it says send. _Avoid_: send checks, validation, preflight.

**Foreground work**: a Gmail call the user is waiting on: a mail action, opening a thread, listing a folder, and whatever the assistant runs on their behalf. It takes the account's quota ahead of background work and waits out a rate limit rather than failing. `mailrs_sync::Priority::Foreground`, which is what work is unless some caller wrapped it in `mailrs_sync::background`; the Google adapter hands the same priority to Gmail's quota bucket. _Avoid_: user action (too narrow, the assistant counts too), interactive.

**Background work**: a Gmail call nobody is waiting on: backfill, history polling, pruning, the inbox check. The sync engine runs its whole tick as background work, which leaves 100 of the account's 250 unit burst for the user and stands aside while a foreground call waits. `mailrs_sync::Priority::Background`, which the Google adapter passes on to Gmail's pacing. _Avoid_: sync work, low priority.

**Whole thread**: a thread the store holds every message of, as a fetch of the thread leaves it. The window keeps messages by date, so a thread in it can lack its older replies; opening a thread trusts the store without asking Gmail only when the thread is whole and a history replay ran in the last 75 seconds. History keeps a whole thread whole, and a new bootstrap's sweep clears the mark on the threads it trims. `threads.whole`, set by the change set's `MarkWhole`. _Avoid_: complete thread, full thread.

**Base subject**: a subject with its reply and forward prefixes, mailing-list tags, and extra spaces gone, in lower case, so "Re: [team] Fwd: Lunch" and "Lunch" agree. `mailrs_domain::subject::base`, alongside `subject::replies`, which says whether a subject carried a reply or forward prefix at all. Local threading is the only reader. _Avoid_: normalised subject, subject key.

**Local threading**: threading done by the store for a server that keeps no threads: a copy of a stored message, or a reply that arrived first, shares its thread; then the nearest message the References and In-Reply-To headers name; then, for a subject with a reply prefix, the nearest message with the same base subject within 30 days. Otherwise the message starts a thread named by its own id. `mailrs_store::threading`, reached through `Change::UpsertLocal`. Gmail supplies its own threads and never runs it. _Avoid_: conversation grouping (the view's setting).

**Inbox check**: the sync engine's comparison of the store's inbox with Gmail's, once when an account starts and then every hour with pruning. It lists Gmail's inbox, and for each stored message whose place in the inbox disagrees it fetches the message again or, when Gmail no longer has it, deletes it. History replay applies each change once, so this is what corrects a message some older write left wrong. `AccountSync::reconcile_inbox`. It waits for the window to finish loading and leaves mail the store has never seen to history, which announces new mail. _Avoid_: full sync, resync, refresh.

**Quota bucket**: the tokens one account may spend at Gmail, refilled at 200 units a second up to a 250 unit burst, under Gmail's own 250 a second. `mailrs_gmail::AccountQuota`, one per address in the OAuth client's `QuotaPool`, plus a project bucket every account waits on. Every call spends from it before it goes out, so batching and pacing show up here rather than in a 429. Only the Google adapter, `mailrs_sync::services::Google`, reaches it; the engine and the window say foreground or background and nothing more. The Google adapter also owns Gmail's prices: which of `messages.get` and `threads.get` a fetch uses, and the page sizes of a listing. _Avoid_: rate limiter, throttle.

**Address book**: the contacts one Google account holds, stored on this computer: each person's name, addresses, photo, organization, and phone number. `mailrs_store::address_book` keeps one per account, and `mailrs_sync::ContactBook` reads it from the People API, walking the pages and keeping the sync token so later refreshes cost one call. It stays empty until the owner turns contacts on in Preferences, and turning them off deletes it. _Avoid_: Google Contacts, contacts (which also names the suggestion list).

**Contact**: one person in an address book, with every address Google holds for them, the primary one first. `mailrs_store::address_book::Contact`. _Avoid_: person, entry, card.

**Correspondent**: someone Penguin Mail found by reading stored mail rather than an address book. `mailrs_store::contacts::Correspondent` scores them by how often they come up, weighing someone written to above someone who only wrote. _Avoid_: contact, sender.

**Recipient suggestion**: one row of what the composer offers while an address is typed, and what search offers for a name. `mailrs_store::contacts::Suggestion` merges the address books with the correspondents: a contact comes first whatever the mail says, and mail orders the contacts among themselves. Each suggestion names the accounts whose address books hold it, and the composer puts the From account's contacts first; the row shows each account's colour dot and short name, or "from mail" for a correspondent (`mailrs::contacts::cue`). _Avoid_: completion, autocomplete entry.

**Contact offer**: the question in the toast after a message goes out, whether to save its new recipients to the contacts of the account that sent it. A recipient is new when that account's address book lacks them and the person has not answered an offer about them on that account (`mailrs_sync::contacts::ContactBook::new_recipients`). Save makes the contacts, and closing the toast counts as no; a toast that runs out of time records nothing, so the next message offers again. Either answer is kept per account and address in `mailrs_store::contact_offers`, so nobody is asked about twice. An account with no contacts service, or with contacts off in Preferences, gets no offer. _Avoid_: prompt, nag, suggestion.

**Recipient chip**: one address in a composer address field, drawn as a pill with a close button. The chips stay out of the Tab chain; Left from the start of the entry reaches them. `mailrs::ui::composer::recipients`. _Avoid_: tag, token, bubble.

**Roving focus**: a row of controls that is one stop on the Tab chain, with the arrow keys moving between its members and Tab returning to the one last used. The formatting bar works this way; the recipient chips take the same arrow keys and never join the Tab chain. `mailrs::ui::roving`. _Avoid_: focus group, tab group.

**Contacts permission**: the access an account grants so Penguin Mail may read its contacts: Google's `contacts` scope, or `Contacts.ReadWrite` for a Microsoft account. It is asked for at sign-in along with every other scope. A person may leave it unticked; without it every `ContactBook` call answers `Permitted::NeedsPermission`, as the settings calls do. _Avoid_: scope, consent.

**Contact change permission**: the access an account grants so Penguin Mail may add and change its contacts, asked for at sign-in along with every other scope. A Microsoft account holds it in the same `Contacts.ReadWrite` scope as the contacts permission, so it has both or neither. Only the assistant's `create_contact` and `update_contact` need it, and they ask again the first time they find it missing; reading contacts needs only the contacts permission. `mailrs::permission::Permission::ChangeContacts`. _Avoid_: write scope, full contacts access.

**Contact card**: what the sender's face or name in a conversation opens: their photo, name, addresses, and organization, with the three things the app already does about a person. `mailrs::ui::contact_card`. A sender in no address book still gets one, built from the message header. _Avoid_: profile, popover, details.
**Invitation**: what one `text/calendar` part of a message says about one event: its title, when it runs, where, who is coming and what each of them said, the organizer, how it repeats, and the UID and sequence that tell one version of an event from the next. `mailrs_domain::invitation::Invitation`. _Avoid_: meeting request, calendar event, ICS.

**Answer**: Yes, No or Maybe. It is what a guest said about an invitation and what the user sends back, so one type covers both. `mailrs_domain::invitation::Answer`. It leaves by whichever of the two roads is open: Google Calendar for an event Google holds, and otherwise a reply. _Avoid_: RSVP, response, PARTSTAT.

**Reply**: the answer as RFC 5546 writes one: a mail to the organizer carrying a `METHOD:REPLY` calendar object with the invitation's UID and sequence, the organizer copied over, and the user as the only attendee. `mailrs_domain::invitation::reply` writes it and `mailrs_sync::invitations` sends it. Nothing but mail takes part, so it reaches an organizer on Exchange, an event Google never filed, and an invitation that arrived at an address the calendar does not belong to. _Avoid_: RSVP email, ICS reply, iTIP message.

**Counter proposal**: asking the organizer for another time, as a `METHOD:COUNTER` object with a new start and end. `mailrs_domain::invitation::counter`, sent the way a reply is. It settles nothing: the event stays where it was until the organizer answers, so the answer buttons stay where they were too. _Avoid_: reschedule, new time request, tentative.

**Scope**: whether an answer or a proposal covers the one occurrence an invitation names or the whole series. `mailrs_domain::invitation::Scope`. An occurrence carries the organizer's own `RECURRENCE-ID` in the reply and points the Google call at that instance; the series carries neither. The card asks only for an invitation that names one occurrence, and every other invitation is a series. _Avoid_: recurrence, range, this and future.

**Clash**: what the user already has on while an invitation's event would run, which the card says in a line: "You have Design crit then." Once the account's calendar copy is synced, the day strip says it instead. `mailrs_sync::Invitations::busy` reads it from the local copy, on the calendars the account owns, and waits for the copy's first read of an account it has never read. An event the user declined, one marked free, a cancelled one and an all-day one leave the hour open. _Avoid_: conflict, overlap, double booking.

**Series**: how a repeating event on the calendar runs: its `RRULE`, and for a rule that stops after a number of occurrences, how many are still to come. `mailrs_domain::calendar::Series`. An invitation to one occurrence carries no rule of its own, so `mailrs_sync::Invitations::series` reads the series the local copy holds under the invitation's UID, whatever the account's provider, and the card shows it in words in the repeat line: "Every Tuesday, 6 left", "Every Monday until 3 March", "Every week, no end date". Without the calendar permission the line stays empty. _Avoid_: recurrence, rule, repeat.

**Repeat choice**: what the editor's Repeats menu and its Custom page set, and the `RRULE` line each choice writes and reads back: Every day, Every weekday, Every week, Every month, Every year, or a custom interval, days of the week and end. `mailrs_domain::calendar::repeat::Repeat`, written by `Repeat::rule` and read back by `Repeat::read`. A rule the menu has no choice for, such as the first Monday of the month, stays as `Repeat::Kept`, whole. Series stays the word for how a series runs; Repeat is only the editor's choice on the way in and out of that rule. _Avoid_: recurrence, repeat rule.

**Invitation change**: what a message does to an event the user already has: it moves it, changes something else about it, or cancels it. `mailrs_sync::invitations::Change`. Only a version with a higher sequence changes anything, and the store keeps what each version changed, so reopening the message says the same thing twice rather than falling silent. Not to be confused with a settings `Change`, which is one named change to the preferences. _Avoid_: update, diff, revision.

**Event card**: the card inside the message that carries an invitation, between its header and its body, that shows the invitation, with Yes, Maybe and No in it, the clash line or the day strip, Propose New Time, and, for one occurrence of a repeating event, the choice between it and the series. `mailrs::ui::invitation::EventCard`. It says under the buttons where the last answer went, since an answer the calendar took shows on the user's own calendar and a mailed reply does not. When the calendar's local copy holds the event on a calendar the user shows, Show in Calendar takes the place of Add to Calendar and opens the calendar on that event. The card is a GTK widget laid over its **card place** in the page, and the message's body goes on being drawn below it, so Google's own links keep working for anyone who declines the calendar permission. _Avoid_: banner, widget, preview.

**Calendar file**: a `text/calendar` part or an `.ics` file that only describes events and asks nothing of the reader, such as a ticket or a booking sent with `METHOD:PUBLISH`, or with no `METHOD` at all. It holds one or several events. `mailrs_domain::invitation::read_all` reads each into an `Invitation`, and `Invitation::card` says which card it gets: `Card::Answer` for a request that stands (Yes, Maybe and No), `Card::News` for a cancellation or somebody's reply, and `Card::Add` for a calendar file. The event card then offers Add to Calendar in place of the answers, with a picker for the calendar and a check button for each event when there are several. `mailrs_sync::Calendar::import` files them through Google's `events.import`, keyed on the UID, so adding the same file twice leaves one event, and the card says "Added to" the calendar and offers Show in Calendar. Penguin Mail also opens a calendar file from Files, in a window of its own (`mailrs::ui::ics_file`), where a request in the file reads as an event to keep. _Avoid_: ticket, attachment, ics import.

**Card place**: the empty element the page keeps in the invitation's message for the event card, as tall as the card. A script in the page reports where it is as the page scrolls and changes, the view lays the card over it, and it takes the keyboard focus in the page's order and hands it to the card. `mailrs::ui::card_place`. _Avoid_: slot, placeholder, anchor.

**Day strip**: the row of hours on the event card: five whole hours around the invitation's event within its day, headed "Your morning", "Your afternoon" or "Your evening", with the account's other events as tinted blocks, the invitation's own dashed and titled "This meeting", and one line, "Nothing else at that hour" or "Clashes with ...". It reads the calendar's local copy, from the calendars the account owns, as the clash line does, and takes the clash line's place once the account's copy is synced. For a series it shows the occurrence Show in Calendar opens. `mailrs::ui::invitation::strip::Strip`. _Avoid_: timeline, mini calendar.

**Calendar permission**: the calendar access an account grants (Google Calendar's scopes, or `Calendars.ReadWrite` for a Microsoft account), asked for at sign-in along with every other scope, which lets Penguin Mail mark an answer on the user's own calendar, ask what else the hour holds, and let the assistant read and change events. It also covers the calendar list, so the local copy can read every calendar rather than the primary one alone; an account that granted the older, narrower scope still gets its primary calendar copied, under its own address, until it grants the list too. A person may leave either half unticked. Without it the answer still reaches the organizer as a reply, and the window offers Grant Access once a run rather than at every press; an assistant calendar tool asks each time it finds the permission missing, since it can do nothing without it. _Avoid_: scope, consent.

**Calendar management permission**: the access an account grants so Penguin Mail may make, rename and delete the calendars it owns (`calendar.calendars`) and change its calendar list (`calendar.calendarlist`): a calendar's colour and Google's hidden flag, and subscribing to a calendar by its address or a public holiday calendar by its id. Asked at sign-in with every other scope. A Microsoft account holds it in `Calendars.ReadWrite`, the same scope as the calendar permission, so it has both or neither. The names above are Google's. An account that signed in before 2026-09-28 holds the read-only list instead, reads every calendar as before, and gets the Grant banner naming "manage calendars". Without it a colour and a hide stay on this computer, and New Calendar, Rename, Delete, Subscribe and Holiday Calendars ask for it. `mailrs::permission::Permission::ManageCalendars`, from `Withheld::calendars` and `Withheld::change_calendar_list`. _Avoid_: calendar write scope.

**Drive permission**: the Google-only access (`drive.file`) an account grants so Penguin Mail may put files in its Google Drive, and only reach the files it put there. Attaching a file from this computer to an event needs it; reading and opening the files an event already has needs only the calendar permission. `mailrs_sync::Withheld::drive`, and "Attach File…" asks for it through Grant Access. A Microsoft account never asks for it: Graph needs no Drive scope, so `Withheld::drive` is always false there. _Avoid_: Drive scope, file permission.

**Event attachment**: a file linked to an event: a Google Drive file with its title, type and `https` link, or a waiting attachment. `mailrs_domain::calendar::Attachment`, in `Event::attachments`. The list is `None` on an event the copy has not read attachments for, and a write then leaves the provider's list alone, since an empty list would take every file off. The popover and the editor list them with an icon by type from the icon theme; Google's own icon link is never loaded. Taking one off an event leaves the file on Drive. _Avoid_: event file, Drive link, attachment (alone, which means a file in a message).

**Waiting attachment**: a file from this computer attached to an event while the upload could not run, kept as the path it was picked from (`Attachment::waiting`). The calendar queue uploads it to Drive before it sends the event, writes the link into the queued change and the copy so a retry never uploads it twice, and sends the event. A file that will not upload holds nothing else up: the event goes out without it and it stays on the event here with an `UploadProblem`. Without the Drive permission it shows "Waiting for access" and the queue tries again once the account grants it; a file no longer at its path, or unreadable, shows "File not found" and the window says so (`TurnedDown::left_out`); a file Drive refuses says why. Only a failure that may pass, such as the network going, keeps the change queued. A read from the provider keeps waiting attachments (`calendar::keep_local`). _Avoid_: pending file, offline attachment.

**Shared attachment**: a file the app uploaded (`Attachment::share` is `Some`) that the event's guests may open. Before the queue sends the event, Drive makes each guest a reader who is not one yet (`calendar::to_share`, `permissions.create` with no mail), so a guest added later gets it on the next save. The editor says "Guests can open this file" and lets the person untick it. Which guests have it (`shared_with`) and the choice live on this computer only, kept across reads from the provider. A file someone else attached is never shared: `drive.file` reaches only the app's own files. _Avoid_: public file, file permission.

**Calendar list edit**: one change to an account's list of calendars rather than to an event: a new calendar, a new name, a colour, hiding one, deleting one, subscribing to one or unsubscribing from one. `mailrs_domain::calendar::list::ListEdit`, made through `CalendarCopy` (`new_calendar`, `rename_calendar`, `recolor_calendar`, `list_calendar`, `delete_calendar`, `subscribe`, `add_public`, `unsubscribe`), shown in the local copy at once and queued in the store (`mailrs_store::calendar_list`) until the next send, which takes the list ahead of the change queue. A calendar made here, or a subscription, is filed under a `new:` id until Google answers with its own, and the send then moves it and everything on it to that id. `mailrs_domain::calendar::list::allows` says which a calendar takes: renaming only one the account owns, deleting one it owns other than its primary; a subscribed, holiday or shared calendar takes neither and is unsubscribed from instead (`calendarList.delete`). A rename also clears the account's own name for the calendar on Google's list (`summaryOverride`), which would otherwise hide the new name. _Avoid_: calendar change (that is an event's), calendar operation.

**Withheld permission**: a scope the person left unticked on Google's or Microsoft's consent screen, or that an account added before this scope existed has never been asked for. `mailrs_sync::Withheld`, read from `AccountServices::withheld` and filled from the account's own granted scopes, by `services::google::withheld` for a Google account and `services::microsoft::withheld` for a Microsoft one; unknown grants withhold nothing, so an account still starting offers everything until a read says otherwise. A feature that finds its scope withheld turns off and says why, rather than surfacing the refusal as an error. _Avoid_: missing scope.

**Grant banner**: the dismiss-free `adw::Banner` at the top of the mail list for an account that has never been through a consent asking for every scope, `app/src/permission.rs`'s `wants_banner`. It names each feature the account lacks (`grant_bar_title`). The calendar shows none: its sidebar says what a withheld calendar lacks on the account's own row. Its Grant Access button is the one place a browser opens for this: `MainWindow::grant_access`, which runs Google's consent for a Google account and Microsoft's for a Microsoft account, which the calendar sidebar row and the Preferences rows for a withheld account also end at. It never opens at start or from the tray, and one consent ends it, granted or not. _Avoid_: consent banner, permission banner.

**Event**: one entry on any calendar of the account, with its id, title, when it runs, where, and who is coming, in the neutral shape every provider maps onto. `mailrs_domain::calendar::Event`; each adapter maps its provider's own shape to it before anything else touches it. `mailrs_sync::Calendar` lists, makes, changes and deletes events for the assistant through the local copy's event change, and tells the guests when the window would (`Calendar::question` words it in the confirmation); a tool names the fields to set as a `mailrs_domain::calendar::EventEdit`. A time goes in and out of the tools as local time, and an all-day event is named by its first and last day, though Google stores the day after the last. Not to be confused with an invitation, which is what one message says about an event. _Avoid_: appointment, meeting, calendar item.

**Free time**: the stretches inside working hours that no busy event touches, unless the user says otherwise for one search. What counts as busy is what counts as a clash: an event declined, marked free, cancelled, or lasting all day leaves the time open, and only a calendar the account owns counts. `mailrs_sync::Calendar::free` reads the local copy; `mailrs_sync::calendar::free_slots` does the arithmetic once the busy stretches are in hand. _Avoid_: availability, gaps, open slots.

**Working hours**: the stretch of the day, and the weekdays, a person keeps meetings in: 09:00 to 18:00, Monday to Friday, unless Preferences says otherwise. `mailrs_domain::calendar::hours::WorkingHours`, kept in `Settings::working_hours`. The Day and Week grid shades what falls outside it, Month shades a day that is not one of its weekdays, and it is what "free time" means unless a search says otherwise. _Avoid_: business hours, office hours.

**Week start**: which day the Week grid, the Month grid and the mini month begin on: the locale's own first weekday, or a fixed Monday or Sunday from Preferences' Week Starts On row. `mailrs_domain::calendar::week::WeekStart`, kept in `Settings::week_start`; `mailrs_domain::calendar::week::week_start` turns it and the locale's own answer into the weekday a grid actually starts on, and `mailrs::locale_time::week_start_weekday` is the one function every grid calls for it. _Avoid_: first day of the week, start of week.

**Calendar**: one calendar on an account, as the calendar view lists it: its name, colour, whether the account may write to it, and whether the view shows it. `mailrs_domain::calendar::Calendar`. The colour from the row's Color menu goes to Google with the calendar management permission (a calendar list edit); without it the store keeps it beside Google's (`mailrs_store::calendar::set_own_color`) and never sends it back. _Avoid_: agenda, schedule.

**Hidden calendar**: a calendar the person took off the calendar sidebar's list with Hide from the List. It leaves the grid as well, and Hidden Calendars at the foot of the list puts it back. The store keeps it (`mailrs_store::calendar::set_listed`), and with the calendar management permission Google's own `hidden` flag follows, so the person's other devices hide it too; a calendar hidden or shown again on another device follows here at the next read of the list (`mailrs_store::calendar_list::save_calendar_list`). A calendar hidden here before the account granted the permission gets Google's flag once, at the first read after the grant (`mailrs_store::calendar_list::queue_local_hides`). `mailrs::ui::calendar::sidebar::take_off_the_list` moves it out of the list. Not the same as an unticked calendar, which stays on the list with its check empty. _Avoid_: removed calendar, deleted calendar.

**Local copy** (calendar): the account's calendars and events kept in the store and read from there, fresh within a minute while the window is open. Every calendar read goes through it: the calendar view, the assistant, the clash line and the series line. A read of an account the copy has never read waits for that first read (`CalendarCopy::ready`). `mailrs_sync::calendar_copy::CalendarCopy`, ticked from the app's own timer as the address book is, not from the mail engine's loop. _Avoid_: cache, mirror.

**CalDAV**: the protocol an IMAP provider's calendar speaks (RFC 4791): collections of iCalendar resources under the account's calendar home, found through the provider table, RFC 6764 or a URL the person typed. `mailrs_dav` speaks it and `mailrs_sync::services::CalDav` puts it behind the calendar service, so the local copy reads a Fastmail calendar the way it reads a Google one. One resource holds a whole series with its changed occurrences. _Avoid_: iCal server, WebCal.

**CardDAV**: the protocol an IMAP provider's contacts speak (RFC 6352): address books of vCards under the account's address book home. `mailrs_sync::services::CardDav` puts it behind the contacts service; the account's contacts are every address book together. _Avoid_: vCard server.

**Calendar scope**: which of an account's calendars an `occurrences` query reads: every one the person has not hidden, every one regardless, or only the ones the account owns, which the clash line and free time use. `mailrs_store::calendar::CalendarScope`. Not to be confused with a mail action's Reach, which is what a button or key acts on. _Avoid_: reach, view.

**Repeat scope**: whether an edit or a delete covers the one occurrence someone picked, that occurrence and every later one, or the whole series. `mailrs_domain::calendar::series::RepeatScope`, the third meaning of "scope" alongside an invitation's answer scope and a calendar scope, kept apart in name so a search or a stack trace lands on the right one. `series::change` and `series::delete` turn a repeat scope into the writes it takes: a changed occurrence of its own, the series cut short with `UNTIL` and a new series picking up where it left off, or the series itself. _Avoid_: scope (bare), range, this and future.

**Occurrence**: one showing of an event on the grid; a series has one per repeat, expanded for the range on screen. `mailrs_domain::calendar::Occurrence`. Each has an id of its own, `Occurrence::id`, in Google's form: the series id, an underscore and the original start in UTC (`standup_20261022T090000Z`, or `standup_20261022` for a whole day). A change or a delete given that id reaches that occurrence alone, never the series. Not to be confused with `invitation::Occurrence`, the one occurrence an invitation names by the `RECURRENCE-ID` it carries. _Avoid_: instance, recurrence.

**Changed occurrence**: one occurrence of a series that no longer matches the rule, kept as an `Event` of its own with `series` naming the series and `original_start` the occurrence it replaces. Its id is `Occurrence::id`'s form built from that original start, `mailrs_domain::calendar::occurrence_id`, and `split_occurrence_id` reads the series and the original start back out of one. A cancelled occurrence is a changed occurrence too, with `status` set to `Cancelled`, so the grid leaves a gap where the series would otherwise show one. _Avoid_: exception, instance.

**Event change**: one change to an event, as the calendar view or the assistant makes it: a new event, an edit of an event or one occurrence (a drag, a nudge, an editor save, an assistant's update), or a removal. `mailrs_sync::calendar_copy::event_change::EventChange`. `CalendarCopy::ask_before` says what to ask first, as a `Question` each caller words its own way, or the `Choice` it settles on when nothing needs asking; `CalendarCopy::change` takes the change, the person's choice of repeat scope and notify, and whether Undo holds it, works out the writes and the notify the account or a guest's own copy forces, and answers a held change or the steps it queued. Nothing outside the copy builds steps or holds them. _Avoid_: edit (that is one kind of event change), mutation, operation.

**Held change**: a calendar edit or delete written to the copy while its Undo toast is up, and not yet in the change queue. `mailrs_sync::calendar_copy::Held`, made by an event change written with `Undo::Offer`: Undo calls `revert`, which puts every row back as it was; the toast closing calls `commit`, which queues the change. A read leaves a held row alone, as it leaves a queued one, and so does the answer to a send of an earlier change of the same event: the commit sends the held change against that answer's etag, and Undo puts the answer back in place of the row. Only one change is held at a time, so holding another commits the one before, and a commit or revert of a change already committed does nothing. `hold` also persists the change's steps (`mailrs_store::calendar::save_holding`), so a crash or a quit before the toast closes still has it to queue: `CalendarCopy::recover_holds` reads any such row once at start and queues it, since no toast survived to offer Undo over it. The calendar view polls `CalendarCopy::still_waiting` while its own toast is up, to close it without an Undo that would do nothing once an assistant edit, which an event change queues at once, commits the change first. _Avoid_: pending change (pending is the clock a queued or held row shows), draft (that is the editor's state).

**Notify**: whether the provider mails an event's guests about one write to it: `Guests` or `Nobody`, sent to Google as `sendUpdates=all` or `none`. `mailrs_domain::calendar::Notify`. A new event and an edit that adds guests always tell them, since that mail is their invitation. A move or a delete of an event with guests asks the person, in the same dialog that confirms the move and asks which occurrences it covers; `CalendarCopy::ask_before` decides what that dialog asks and `ui::calendar::scope` words it. The choice rides the held change and the queued row, so it outlives an Undo toast, a restart and going offline; when two writes of one event fold into one queued change, telling the guests wins unless a delete replaces an unsent edit. Graph always mails the guests, so a Microsoft account never offers to skip mailing them, its dialog gives no choice about the guests (`event_change::Facts::always_mails`), and its queue records `Guests` for every change. A guest's change to their own copy of an invitation, and its removal (the popover's Remove), go out as `Nobody` whatever was asked: they touch only the guest's own copy, and Google marks a guest who removes one declined itself. `CalendarCopy::change` applies both rules, for the window and the assistant alike. _Avoid_: send updates, notification (that is a reminder on this computer).

**Event kind**: what sort of entry an event is, Google's `eventType`: an ordinary event, out of office, focus time, a working location or a birthday. `mailrs_domain::calendar::Kind`. Out of office and focus time can decline the meetings that fall in them (`Declines`, with a message); the editor, the New Event menu and quick add make both, on a primary calendar only, and only where `Offers` says the provider keeps them: Google Workspace keeps both with their declines, Outlook keeps out of office (Graph's `showAs: oof`) without a decline choice, and a personal Gmail account, CalDAV and POP3 keep neither. `mailrs::ui::calendar::draft::creatable_types` reads the offer for one calendar, and `Draft::new_as` gives each type its defaults: focus time two hours from the picked time, out of office whole days from today through the picked day. Google refuses an all-day out of office, so it runs from one local midnight to another, and the week and day views draw a timed entry like that with the all-day ones (`layout::whole_days`). Google's own apps make working locations and birthdays, so the calendar shows them read-only and the assistant may not change them. A working location is never an event block: its place sits under the day's heading. `mailrs::ui::calendar::kinds` says how each kind looks and reads. _Avoid_: event type (the Rust keyword clash), status event.

**Event block**: the button `TimeGrid` and `AllDayStrip` draw for one placed occurrence: a bar in the calendar's or the event's own colour, the title and the time, dashed while the account has not answered it and struck through once it has declined. `mailrs::ui::calendar::block::EventBlock`. Named apart from "Event card", which is the invitation card a message shows (`mailrs::ui::invitation::EventCard`), so the two never collide in a search or a stack trace. _Avoid_: event card, event cell.

**Agenda**: the calendar page's flat list of upcoming occurrences, a heading per date then a row per occurrence, in place of a grid. `mailrs::ui::calendar::agenda::Agenda`, a `gtk::ListView` over a model that also answers `gtk::SectionModel` for the date headings, so a widget exists only for the rows on screen; loading earlier days grows the same list rather than opening a new one. The Calendar entry's "_Avoid_: agenda" is about naming a calendar, not this list. _Avoid_: timeline, list view (that is any widget of the kind).

**Space**: what the window shows beside the sidebar, the mail or the calendar, picked with the switch at the top of the sidebar (Alt+1, Alt+2) and remembered for the next start. The sidebar stays on screen in both and shows the mailboxes or the calendar's own sidebar. `mailrs::settings::Space`; the window holds the two in a stack named `spaces`. While the calendar shows, mail's keys and chords leave the hidden conversation alone. Each toggle of the switch carries a badge for the space away from the screen: Mail the unified inbox's unread count, Calendar the invitations waiting for an answer (`mailrs::ui::sidebar::space_badges`). _Avoid_: mode, tab, page (a page is one screen of a navigation view).

**Change queue**: calendar edits made here that the provider has not taken yet, sent in order; a change the provider turns down leaves the queue and the provider's version stays. Moving an event to another calendar of its account is a row of its own (`ChangeKind::Move`, Google's `events.move`) under the calendar it leaves, and the edit saved with it waits on it. `mailrs_store::calendar::QueuedChange`. _Avoid_: outbox (that is mail's).

**Event reminder**: a desktop notification before a calendar event, at the minutes the event names or, when it names none, at its calendar's defaults. Only reminders set to notify go up; email reminders are the provider's to send. Each one goes up once per occurrence, and the store remembers it (`mailrs_store::event_reminders`), so the restart after the window closes does not repeat it. One that passed while the computer slept goes up on waking while its event still runs. Snooze brings it back five minutes later. `mailrs::event_reminders::plan` decides what is due. _Avoid_: alarm, alert, Remind Me (that is mail's).

**Turned down**: a change made here that the provider refused when the queue tried to send it, such as an event changed elsewhere first or a calendar gone read-only; the local copy takes the provider's version in its place. `mailrs_sync::calendar_copy::TurnedDown`. _Avoid_: conflict, rejected change.

**Send-as address**: one address an account may send mail as: its own, an address verified by Gmail, or one the owner configured for an IMAP or POP3 account. SMTP accounts keep their addresses locally and use the same outgoing server and credentials for each. Gmail keeps a display name and a signature per address, so choosing one chooses all three. `mailrs_sync::SendAsAddress` is what `IdentityService::identities` reports and `AccountSettings::send_as` hands the app; `mailrs::compose::SendAsAddress` is the copy Preferences keeps, so a composer opens without waiting on the network. An alias Gmail has not verified is left out, since Gmail would refuse to send from it. _Avoid_: alias, from address, sender.

**Address suffix**: text appended to a configured send-as address before `@`, including its `+` or `.` separator. Each separator is enabled per address; only that base and domain match. A suffix keeps its base address's name and signature. Replies recognize it in To or Cc, and Reply All excludes it from the recipients. `mailrs::compose::Suffixes`. _Avoid_: wildcard address, catch-all.

**Identity**: one row of the composer's From list: a send-as address with the account it belongs to, the display name, and the signature that goes with it. `mailrs::compose::Identity`. A reply opens on the identity the mail was written to, a new message on that account's default address. _Avoid_: account, profile, persona.

**Signature**: the text Gmail keeps for one send-as address, which goes below what the person writes. Whoever opens a composer or sends a message says whether it gets one through `mailrs::app::Signature`: `Add` for a message Penguin Mail starts (new, reply, forward, or one the assistant writes), `AsWritten` for one a composer opened before, which added it then (a saved draft, an undone send, a message back from the outbox), and for a request the person never wrote, such as unsubscribe mail. A new message comes from the account Preferences names, else the one on screen, else the first; `App::new_message` applies that rule. _Avoid_: footer, sign-off.

**Prose**: the parts of a draft a dictionary should judge. A quoted reply and a code block are not prose, because the buffer gives those lines their own kind; nor is a list marker, a run of inline code, or a picture, because those carry their own tags; nor is a word with a digit, an underscore, an `@` or a slash in it, because that is an address or an identifier. `mailrs::ui::composer::spell` reads all of this off the buffer rather than the text, so rich text and Markdown answer the same way. _Avoid_: body, content, checkable text.

**Squiggle**: the mark under a misspelling: a `gtk::TextTag` named `misspelled` with Pango's error underline. It lies beside the characters rather than in them, so it shows through bold, a link or a list, and it cannot reach the message: `richbuffer::read` builds the rich body from the block kinds, the four style tags and the link tags, and asks about nothing else. _Avoid_: highlight, underline, marker.

**Notification button**: one of Archive, Mark as Read, Delete and Reply on a new-mail desktop notification. `mailrs::notify::Button`, and Preferences chooses which of the four appear. A daemon that does not advertise the `actions` capability gets a plain notification with none of them, and the body still opens the conversation. The three that change mail go through `MailActions`, so they batch per account and Undo reverses them; Reply opens a composer. _Avoid_: notification action, hint.

**Template**: a saved body the composer drops into a message, with a name and an optional subject. `mailrs_store::templates::Template` keeps it as Markdown, which is what a rich body reads and writes, so an inserted template arrives with its styling. A template follows the person rather than an account, so every account sees the same list. _Avoid_: canned reply, snippet, boilerplate.

**Promise**: a phrase in what the writer typed that says a file is coming, such as "see attached" or "segue em anexo", with the sentence it sits in. `mailrs::attachcheck::promised` finds one in the subject and the body, reading only the writer's own words: the quoted original, the forwarded message and the signature are cut off first, and a link that spells out a phrase does not count. The composer asks before sending a message that makes a promise and carries no file, and Preferences turns the question off. _Avoid_: reminder, warning, attachment hint.

**Placeholder**: a name in double braces that a template fills in as it goes into a message: `{{first_name}}`, `{{name}}` and `{{email}}` from the first recipient, `{{subject}}`, and `{{date}}`. `mailrs::templates::expand` fills them on the way in rather than on the way out, so the saved template still reads `{{first_name}}` the next time; a name it does not know stays as written, since a body may hold braces of its own. _Avoid_: variable, token, merge field.

**Signature**: what the person's gpg made of a signed part: who signed it, whether the text is the text that was signed, and how far the trust database vouches for the signer. `mailrs_pgp::Signature`, which also lists every user id on the signing key with its own validity. The verdict and the trust answer different questions, so a key nobody has vouched for still gives a good signature, and a signature from a key this computer lacks is unchecked rather than bad. _Avoid_: verification result, signature check, validation.

**Canonical part**: the bytes a signature is actually made over: the part with CRLF line endings throughout and anything a mail server might rewrite encoded out of reach, which means whitespace at the end of a line and bytes above ASCII. `mailrs_pgp::mime::canonical` makes it, and the same bytes go into the message, so the two cannot drift apart. _Avoid_: normalized body, cleaned part.

**Inline PGP**: armor written into a `text/plain` body rather than into MIME parts, either an encrypted message or text left readable with its signature underneath. `mailrs_pgp::inline` finds the block among whatever a mail client wrote around it and opens it. RFC 3156 came later and never replaced the habit. _Avoid_: legacy PGP, armored text.

**Recipient key**: what gpg holds for one address a message is going to: a key it would encrypt to, or nothing. `mailrs_pgp::Recipient`. The composer offers encryption when every recipient has one and names the ones that do not; how far each key is trusted belongs in a warning, not in that decision. _Avoid_: public key, certificate, contact key.

**Mark**: what the protection card says about a message: a line naming what happened, a line saying how much it is worth, and which of the three tones the card takes. `mailrs::protection::Mark`, which both engines fill. Good, bad and unchecked stay three answers rather than two, because a signature from a key this computer lacks is not a bad signature. The good tone says who wrote the message, so a good signature earns it only when the key or certificate names the address in From and the person's own trust reaches that address: a vouched OpenPGP user id, or an S/MIME chain to a trusted root. A key nobody vouched for, or one that names somebody other than the sender, gives an unchecked card that says which. `protection::read` is the one place that weighs it. _Avoid_: status, badge, verdict (which is the engine's word for one half of this).

**Protection card**: the card above the message body that shows a mark. `mailrs::ui::pgp::PgpCard`, named for the standard it was built for and since taken over by both. It sits above the translation card, has no buttons, and stays put once the engine has answered, so a message that was opened out of its ciphertext goes on saying it arrived encrypted. _Avoid_: banner, badge, security indicator.

**Protection**: the wrapper a message arrived in and the standard that wrote it: `multipart/signed` or `multipart/encrypted` under RFC 3156, and under S/MIME the same `multipart/signed` plus the two blob shapes of `application/pkcs7-mime`. `mailrs_domain::Protection`, which `mailrs_mime::read` reads off the top-level part and only there, since a signed part further down belongs to a message somebody forwarded. Naming the standard is how the app knows which engine opens the message. The signature covers the bytes as they were sent, so whoever checks one fetches the raw message; until then the body holds only the first part of a `multipart/signed`, the one a signature claims to cover. Inline PGP carries no wrapper and is found in the text instead. `mailrs::protection` is the app's side of all this: the mark both engines fill, the MIME they read the same way, and `protection::engine`, which is where a message goes to find out which of the two it needs. `mailrs::pgp` and `mailrs::smime` are the two adapters over it, and neither knows the other. _Avoid_: encryption status, security level.

**Engine finding**: what gpg or gpgsm found in one protected message, in words neither standard owns: whether it arrived encrypted, the signature over it (a verdict, the signer, and how far the person's own trust reaches that signer), and the part the engine checked or opened. `mailrs::protection::Found`, which each adapter fills and `protection::read` alone turns into a mark and a body. That body is always cut from the part the engine checked or opened, so a third part in a `multipart/signed`, or text written around inline armor, never shows under the card. _Avoid_: result, verification result.

**GnuPG runner**: the one way both engines start `gpg` or `gpgsm`: `mailrs_pgp::gnupg::Program::run`. It writes the input while it reads the output, reads the status lines from a pipe of their own rather than from stderr, and takes a `Pinentry` on every run, `Never` for anything that only reads or encrypts and `MayAsk` for decrypting, signing and importing a file the person picked, so no new call can put a window in front of the person by forgetting a flag. `Run::signatures` reads every signature the status lines describe, for either program. _Avoid_: wrapper, gpg helper.

**Key import**: putting the keys or certificates in a file the person picked into the GnuPG home the app runs against, `GNUPGHOME` when it is set, as the snap sets it. `Pgp::import` and `Smime::import` each return one `mailrs_pgp::gnupg::Import` per key or certificate, with its `Change` (new, updated, unchanged), whether the file carried its secret key, and the name and address on it. Preferences offers it beside the OpenPGP and S/MIME rows (`mailrs::ui::key_import`). A PKCS#12 file opens with a passphrase the person's pinentry asks for. _Avoid_: key upload, key load.

**Remembered verdict**: what the engine said about a signed message that arrived in the clear, kept in memory for the rest of the run so reopening the conversation draws the card without fetching the raw message or starting gpg. `mailrs::protection::remembered::Verdicts`, keyed by message id and held only while the keyring's newest change time stays the one it was read against. Nothing from an encrypted message is kept, and an engine failure is not kept either. _Avoid_: cache (in wording the user reads), stored signature.

**Claim**: the "ask the engine once" mark on one protected message, taken before anything is awaited. An engine run claims every protected message of the thread that has none yet, newest first, and asks about them one at a time. `mailrs::protection::run::Claimed` is one message with that mark already set, so holding one says no second pinentry can open for it while this run lasts. A message whose engine this computer lacks is left unclaimed and reads on the day that engine turns up. _Avoid_: lock, reservation, token.

**Wanted**: the conversation an answer belongs to, and the only way a run reaches its effect port. `mailrs::wanted::Wanted` holds the target the run started on, the account, the thread, and the one message when the view shows one, and hands an answer back while that target is on screen and nothing otherwise, so the question a window task must ask after every await is asked for it: the reader may have opened something else while gpg held a pinentry or Gmail answered, and an answer they are no longer waiting for has nowhere to go. The engine run and the thread run share it; the calendar run keys it on a ticket for a part of the calendar page rather than a conversation. _Avoid_: stale check, guard, cancellation.

**Open thread**: the conversation on screen as plain data: its messages and bodies, which ones the reader opened, what they allowed, and what the engine and the model made of it. `mailrs::open_thread::OpenThread`. It builds the page itself, in `page`: which body each message shows, the cleaned HTML kept for each, and, through `prose`, which message a translation reads. The conversation view loads that page, changes the thread only through named changes, and keeps only what WebKit needs: the content filter and the background colour. The runs read it through their desks. _Avoid_: current thread, selection, model.

**Quoted history**: the earlier messages a reply or forward carries under what its writer wrote: a Gmail, Outlook, Apple Mail, Thunderbird or Penguin Mail quote with the line that says who wrote it, a trailing run of `>` lines in plain text, or a forwarded message. `mailrs::quoted` finds it when a body is cleaned, only at the end of the message and only under something the writer wrote, and the page folds it behind a "Show trimmed content" button. A quote with the writer's answers after it is an interleaved reply and stays shown. The composer folds a reply's quote and a forwarded message the same way: the draft holds them outside the editor (`Draft::quoted`, `Draft::forwarded`) and sends them under the words, "•••" puts a quote in the body to edit and shows a forwarded message read-only under the editor, and × drops them. A draft saved folded marks the quote's start in its HTML with the comment `<!-- mailrs-quoted -->`. _Avoid_: trimmed content, quote block, thread history.

**Inline picture**: a picture an HTML body names by `cid:`, which arrived as a part of the same message. `mailrs::open_thread::InlineImage`. Cleaning points each at an address of the app's own `mailrs-cid` scheme, with the account, the message and a version in it, and the conversation view serves the bytes from the open thread; they never go into the page. The pictures arrive after the text, as a step of the thread run, and the page's requests wait for them. An engine that opens a message replaces its pictures under a new version, so WebKit cannot answer from a picture it kept of the old ones. _Avoid_: embedded image, attachment (which the rows below the message list).

**Picture description**: the words that stand for a picture in a message being written. They go out as the picture's alt text, and a screen reader names the picture by them in the composer. `mailrs::ui::composer::richbuffer::Placed::alt`. A picture keeps the description the HTML it came from gave it, one inserted from a file starts with the file's name, and the writer changes it with Describe Picture on the picture's right-click menu. _Avoid_: caption (words shown under a picture), title.

**Part path**: where a file sits in a message, as IMAP numbers the parts: "1" for the body of a message that is not multipart, "2" for the second part of a multipart, "1.3" for the third part inside the first. `mailrs_mime::part` cuts a file out of a raw message by it, the Google adapter fetches one file of a large message by it, and the store keeps it as the file's `part_id` and `attachment_id`. _Avoid_: attachment id, part id.

**Raw limit**: the size, 2 MB, under which a message is fetched raw and read whole. A message at or over it, or of unknown size, is fetched as its structure and its text parts, and each file comes alone when someone opens or saves it. `mailrs_sync::RAW_LIMIT`, compared with the size the listing reported (Gmail's `sizeEstimate`). Both paths give the same body and the same part paths. _Avoid_: size cap, threshold.

**Raw cache**: the last small messages an account fetched whole, kept in memory up to 16 MiB per account. `mailrs_sync::raw_cache::RawCache`, which `AccountSync` reads before it asks the server, so a file saved, a picture drawn or a signature checked right after a small message opened costs no second fetch. A message at or over the raw limit never enters it. _Avoid_: message cache (the body cache is on disk and holds text).

**Patch**: the `<article>` elements of the page on screen that a change touched, with their new HTML, which the conversation view puts in place of the old ones instead of loading the page again. `mailrs::open_thread::Page::Patch`. `OpenThread::page` keeps a hash of the head and of each article it last handed out and answers a patch while the head and the list of messages stay the same; a new theme, remote images allowed, or a message joining or leaving the thread loads the whole page. The view holds a patch until WebKit has parsed the latest page, and keeps the first message on screen where it was. _Avoid_: diff, update, partial reload.

**Calendar run**: every read the calendar view makes from the local copy, and the one rule for an answer that comes back late. `mailrs::ui::calendar::run::CalendarRun` reads each carousel page, the calendar list and mini month, "Waiting for your answer", the narrow list and its earlier and later days, the search results and the older events a range needs, opens the event Show in Calendar asks for once its page, or the narrow list in a narrow window, has drawn, and makes a move, a delete or an editor save one event change with its question, Undo toast and reload. The next-event card's reads (`NextCard`) keep the same rule. Each read starts with a ticket for the part of the page it fills, and its answer lands only while it is the newest read for that part and the part still shows what it was asked for, such as the same week. _Avoid_: loader, controller, generation, read counter.

**Thread run**: the life of the open thread, from the click to the last card. `mailrs::open_thread::run::ThreadRun` shows the stored copy, fetches the whole thread and its bodies, marks it read after the delay, fetches the pictures for the attachment rows, reads the invitation and what clashes with it, offers and makes a translation, starts the engine run, and refreshes the thread when the store changes under it. _Avoid_: loader, controller, thread manager.

**Stale**: what an event on the open thread leaves out of date: the translation card, the engine run's claim, the event card, the inline pictures, the pictures on the attachment rows, the unread mark. `mailrs::open_thread::run::Stale::after` names them for each event, so a new body brings every card up to date and a decrypted one rereads its invitation and language without asking the engine again. The page and the header buttons are not in it, because each named change on the view redraws what it touched. _Avoid_: dirty flags, invalidation.

**Certificate**: what gpgsm holds for one address: the subject it names, the address on it, and its fingerprint. `mailrs_smime::Certificate`. Only one whose chain reaches a root in the person's trust list counts for encryption, because gpgsm files away every certificate a signature carries when it checks that signature, and a certificate a stranger mailed in would otherwise take the next message meant for the address it names. The composer offers encryption when every recipient has such a certificate and names the ones who do not. _Avoid_: key, public key, cert.

**Chain**: how far the line of certificates behind a signature got: to a root in the person's own trust list, or not that far. `mailrs_smime::Chain`. It answers who the signer is, which is a different question from whether the text is the text that was signed, and a corporate certificate from an authority this computer has never been told about gives a good signature with an untrusted chain. A chain can also reach a trusted root with its revocation unknown: gpgsm could not learn from the certificate authority, within ten seconds, whether a certificate on it was revoked. The card then names the signer in the neutral tone and says the revocation went unchecked. _Avoid_: trust, validation, path.

**Revocation check**: gpgsm asking dirmngr, and dirmngr asking the certificate authority's server for its CRL, whether a certificate on a chain was taken back. `mailrs_smime::Smime::verify` gives it ten seconds, then kills that gpgsm run and checks the signature again without it, so an offline computer or a slow authority never keeps a message closed. _Avoid_: CRL check (in wording the user reads), OCSP, validity check.

**Standard**: which of the two, OpenPGP or S/MIME, signs or encrypts a message on the way out. `mailrs::protection::Standard`, which the composer sets on the draft: the recipients decide it for an encrypted message and the sender's own key or certificate for one that is only signed. OpenPGP wins when both could carry it, so that nothing about a message the app already knew how to send changes the day gpgsm turns up. _Avoid_: scheme, protocol, format.

**Hidden recipient**: a reader of an encrypted message whose key id gpg leaves out of it (`--hidden-recipient`), so the others can tell somebody else holds a key to it and not who. It is how a Bcc stays blind under OpenPGP. `mailrs_pgp::Readers::hidden`, which `mailrs::protection::Addressees` fills from the draft's Bcc, less anyone To, Cc or From names anyway. S/MIME has no such thing, since CMS names every recipient inside the envelope, so the composer will not encrypt a draft with a Bcc under S/MIME. _Avoid_: anonymous recipient, throw-keyids.

**Encrypted draft**: a draft whose message is meant to go out encrypted, which Gmail keeps with its headers readable and its body encrypted to the writer's own key or certificate alone, marked `X-Penguin-Mail-Draft: encrypt` (`; sign` when Sign was on). `mailrs::protection::draft` writes it when the composer or the assistant's `edit_draft` saves (`save`), and opens it again when the window's Edit or `edit_draft` reopens it (`reopened`), with a pinentry if the engine wants one. The recipients' keys play no part until the message is sent. _Avoid_: secret draft, sealed draft.

**Find bar**: the bar Ctrl+F puts over an open conversation, holding the query, the count of matches, and an arrow each way. `mailrs::ui::find::FindBar` asks WebKit's own `FindController` for the text and counts the steps itself, since WebKit reports how many matches a page holds but never which one it highlighted. A query in lower case matches either case and a capital asks for that capital. Every message of the thread opens while the bar is up, because the stylesheet hides a closed message's body and WebKit finds nothing there. _Avoid_: search bar, which is the mailbox search, filter.

**Translation**: one message's prose in the chosen AI language, made by the model chosen for translation when the reader asks for it. `mailrs::translation` counts the commonest words of a handful of languages to tell what the message is in, cuts the prose out of the body the page draws, sends the pieces and nothing else, and puts each one back where it came from, so a bank statement stays the table the bank wrote. It lasts as long as the thread stays open and never reaches the store, because it is text a model derived and tomorrow's model would write it differently. Nothing is sent until the button is pressed: with a local server the words stay on this computer and with Anthropic or a Claude subscription they do not, and the card says which before anything goes out. _Avoid_: machine translation, localization (which is the interface's own words, in `mailrs::language`).

**Translation card**: the card above the message, saying what language the message is in and where its words would go to be translated. Once there is a translation it names what the message came from, and its button turns the message back to what arrived and forward again, which costs no second request. `mailrs::ui::translation::TranslationCard`. It appears while the words read as another language, or the chosen AI language has no local detector. _Avoid_: banner, translate bar.

**Release**: a version published on GitHub from a `vX.Y.Z` tag, with a .deb, a tarball, a zip, `SHA256SUMS`, and its section of `CHANGELOG.md`. `scripts/release.sh` makes the tag and the release workflow builds the rest. `mailrs::update::version::Release` is what the app reads of one. _Avoid_: build, version (for the published thing).

**Update**: installing a newer release over the running copy, the way that copy was installed: apt behind a password prompt for the .deb under `/usr`, the tarball's own `install-files.sh` for a copy under the person's home. The app then restarts into it in place. A copy run from a cargo build or as the demo never updates. `mailrs::update`. _Avoid_: upgrade, patch.

**Newsletter**: a sender whose mail carries a `List-Unsubscribe` header, or an unsubscribe link in its body. `mailrs_store::newsletters::list` groups the last 90 days of an account's mail by sender address to find them, so the assistant can be asked what the person is on and leave several at once. Gmail's Promotions, Updates and Forums categories catch the rest: a sender whose header the store has not kept still counts, and `mailrs_sync::Newsletters::list` fetches the header for the ones that write often enough to be worth a call. _Avoid_: mailing list, bulk sender, subscription.

**Way out**: how one newsletter lets go, in the order Penguin Mail tries them: the header's one-click POST, the header's web page, the header's `mailto:`, then a link in the body when the header offers none. `mailrs_sync::unsubscribe::Unsubscribe`, picked by `choose_with_body`. A page comes before a mail request because a mail request often does nothing and a page is what works. A body link comes last because it is whatever the sender made it. The one-click POST goes to the list's own server through `mailrs_sync::OneClick`, never through the account's provider; tests and the demo post to `FakeOneClick`. _Avoid_: unsubscribe method, opt-out channel.

**Left list**: a newsletter the person unsubscribed from, kept by the sender's lower-case address with how it was left (`one_click`, `page` or `email`) and when. `mailrs_store::unsubscribes`, written through `mailrs_sync::MailActions::left` by the window and the assistant once a list let go, never for a request still in the Outbox. A conversation from a left list opens with no Unsubscribe banner, and `list_newsletters` marks the sender as left. _Avoid_: unsubscription, opt-out record.

**Unsubscribe page**: the page a way out leads to, loaded out of sight and read as data. `mailrs::unsubscribe_page::PageForm` is its address, its title, its visible text and the fields and buttons of its forms, with no markup in it, so neither the rules nor a model see what the sender wrote. `pick` answers a `Plan`, which names by id the fields to fill, the boxes to tick and the button to press, or says it is unsure and the page opens in the person's browser instead. `prepare` reads and decides, the person says yes, `finish` submits. The only text it ever types into a page is the address the newsletter was sent to. _Avoid_: preference centre, opt-out form, landing page.

**Packaging**: the kind of package a build is for: native (the .deb, the tarball and a build from source), rpm, Arch, Flatpak or Snap, chosen at build time with the cargo features `packaging-rpm`, `packaging-arch`, `packaging-flatpak` and `packaging-snap`. `mailrs::packaging::BUILT_FOR`. It decides who installs new versions, dnf, pacman, Flathub or the Snap Store for their packages and the app itself for the rest, and whether skills run: a skill's sandbox cannot start inside the one Flatpak or a snap puts the app in, so both turn skills off. _Avoid_: distribution, flavour, channel.

**Release key**: the OpenPGP key that signs the apt and dnf repositories and each release's `SHA256SUMS`, fingerprint `FE3C3B6E699AF939DC4670DCF3A853035C3E2B8E`. The app carries its public half, `mailrs::update::signature::RELEASE_KEY`, read from `packaging/apt/penguin-mail-archive-keyring.gpg` at build time, and trusts the sums of a release it installs only when `SHA256SUMS.asc` is a good signature by it. The release workflow reads the private half from the `APT_SIGNING_KEY` secret. _Avoid_: signing key, archive key, GPG key.

**Backend error**: what went wrong on a mail server's side, as a kind every provider shares: the account needs to sign in again, the network is down, the server is rate limiting, something is not found, the server lost its place, a permission is missing, the server refused, or it cannot do that at all. `mailrs_sync::BackendError`, carried as `SyncError::Backend`. The retry rules and the account states read the kind. What only Gmail can say, such as an API switched off in the Cloud project, stays in its `Gmail` variant, and a kind that stands for a Gmail error keeps Gmail's wording. _Avoid_: Gmail error (outside the Google adapter), API error.

**Service**: one kind of work an account can be asked for: mail, calendar, contacts, rules, the automatic reply, or the addresses it sends as. Each is a trait in `mailrs_sync::services` (`MailBackend`, `CalendarService`, `ContactsService`, `RulesService`, `AutoReplyService`, `IdentityService`), and a provider's adapter implements the ones it offers. `services::Google` works over any `GmailApi`, the real client or `FakeGmail`, maps Gmail's errors to backend errors, and keeps Gmail's quota to itself. `services::Imap` serves an IMAP account's mail; `services::Microsoft` serves a Microsoft account over any `GraphApi`, the real client or `FakeGraph`. An IMAP or POP3 account's calendar comes from `services::CalDav`, which mails the answer to an invitation through the account's `AnyMail`, its contacts from `services::CardDav`, and an IMAP account's rules and automatic reply from `services::SieveRules`, or its rules from `services::LocalRules` on this computer when the server runs none. `IdentityService` answers send-as addresses and has nothing to do with the composer's identity. _Avoid_: API, backend (for anything but mail).

**Capability**: a fact about what an account's mail service can do: whether a message can sit in several server mailboxes, whether the server keeps threads, files its own sent mail, sorts the inbox into categories, and can erase mail for good; which keywords it stores; whether it reads a search in its own syntax; whether a message takes a new name on the server when it moves, whether the change feed restates a changed message whole, whether the account keeps tags, and whether it sorts its inbox into Focused and Other; and the most messages one write may name. `mailrs_sync::MailCapabilities`, from `MailBackend::capabilities`. Gmail has all of the first group and none of those four, stores `$seen`, `$flagged` and `$muted`, reads Gmail's search syntax, and takes a thousand messages a write. IMAP renames and has no tags, restating feed or Focused. `ops_for` reads the first to choose between filing and moving. The window and the assistant read capabilities through `Offers`. _Avoid_: feature, support flag.

**Delta link**: the link Graph hands back at the end of one round of a folder's (or a calendar's, or a contact folder's) changes; following it answers what changed since, and a next link partway through a round is followed the same way. The Microsoft adapter keeps one per synced folder in the account's sync state, as JSON. One Graph no longer keeps answers `StateLost`, and the engine lists the mail again. `mailrs_sync::services::microsoft`. _Avoid_: sync token (Google's), cursor.

**Immutable id**: Graph's id for a message that stays the same when the message moves, which every call asks for (`Prefer: IdType="ImmutableId"`). It is why a Microsoft account keeps no remote refs: the store's id is Graph's. _Avoid_: permanent id, stable id.

**Account services**: the services one account is served by, one closed enum per kind of work (`AnyMail`, `AnyCalendar`, `AnyContacts`, `AnyRules`, `AnyAutoReply`, `AnyIdentities`) with one variant for each adapter, so every call is a `match` and nothing is boxed. Each adapter runs over a client enum (`AnyGmail`, `AnyGraph`, `AnyImap`, `AnySmtp`, `AnyPop3`, `AnyDav`, `AnySieve`) that holds the real client or, under the `fake` feature, the in-memory one. `mailrs_sync::AccountServices`, built by `AccountServices::google` for a signed-in Google account and `AccountServices::microsoft` for a Microsoft one, which `connect` picks by the account's **provider**, and `connect_imap` for an IMAP one, which adds the calendar, contacts, rules and automatic reply of each confirmed server. Tests and the demo hand the same constructors an in-memory client, such as `AccountServices::google(Arc<FakeGmail>)`. A service the provider lacks is `None`, and the module that needs it answers `BackendError::Unsupported`; the calendar, contacts, rules and the automatic reply are optional this way. _Avoid_: client, API, backend.

**Offers**: what one account can do, read from its services for the window and the assistant: whether mail takes labels or moves between folders, whether the inbox has categories, whether mail can be erased for good, whether the account has a calendar, contacts, rules and an automatic reply, and whether its server searches past the mail on this computer. It also holds whether the account keeps tags (Tags… beside Move to Folder), whether the inbox splits into Focused and Other (the Focused and Other tabs), and the calendar gates: `event_files` (attaching a file to an event), `moves_events` (moving an event to another calendar), `calendar_list` (a new calendar, a rename, a colour, a subscription, removing one), `subscriptions` (subscribing by address, a holiday calendar and unsubscribing, which Google offers and Outlook does not), `out_of_office` and `focus_time` (the event kinds a new entry on the primary calendar can take), and `declines` (whether those keep a decline choice and message). Google Workspace offers the last three; a personal Google account, told apart by a `gmail.com` or `googlemail.com` address (`services::is_workspace`), offers none of them, and Outlook offers `out_of_office` alone. Gmail offers the three calendar gates, IMAP none; the window hides an action the account does not offer, and no adapter is asked for it. `mailrs_sync::Offers`; `Missing` names one thing it lacks, and `mailrs::offered::reason` says why in a line worded for the provider. An account that has not started offers everything until it does. _Avoid_: features, permissions (a permission is what the person grants).

**Filing**: how the accounts in question file mail, and so the words the window uses for it: with labels, several on one message, or in folders, one per message. It is folders only when every account in question files in folders. Labels, Move to Folder, New Label or New Folder, and the Rename and Delete dialogs follow it; deleting a label leaves its mail, while deleting a folder deletes the mail in it. Mail from several accounts takes a label by name only when every one of them files with labels (`Filing::across`). On a folder account every action that puts mail somewhere moves it there, a drop from Flagged or a search included, and mail that leaves a folder with nowhere named goes to the Archive; two folders at once is refused. The Labels button and the Keyboard Shortcuts window follow it too: the button reads as its picker does, by the mailbox's accounts with nothing picked and by `Filing::across` for mail from several accounts (`Filing::picker`). `mailrs::offered::Filing`. _Avoid_: label mode, folder mode.

**Label order**: where the person put each of an account's labels or folders among its siblings in the sidebar, by dragging a row or with Move Up and Move Down. Neither Gmail nor IMAP keeps one, so it lives on this computer alone, in the `position` column of the `mailboxes` table; labels never moved follow the others by name. Dropping a label inside another, or beside a label at another depth, renames it through `AccountSync::place_label`, which stores the new siblings' order in the same write. `ui::sidebar::tree` decides where a drop lands and which drops to refuse. _Avoid_: sort order, label rank.

**Move to Folder**: what the Labels button and menu item become on an account that files in folders: choosing a folder moves the mail there instead of adding a label, which on that server would leave a copy behind. It runs `TriageAction::MoveTo` with the folder's id, which `ops_for` turns into `MailOp::MoveToMailbox` on a folder server, and into filing in the mailbox and leaving the inbox on Gmail, as Gmail's own Move to does. The assistant's label tool does the same when an account files in folders and it is given one folder to add. _Avoid_: file, copy to folder.

**Provider**: the company or protocol serving an account's mail: Gmail, Microsoft for Outlook.com and Microsoft 365, or IMAP for any other server. `mailrs_domain::Provider`, kept in `accounts.provider`; it picks which adapter serves the account. An IMAP account also keeps who runs its server as the person knows them, such as Fastmail, in `accounts.provider_name`, and its two servers in `account_servers`; `Account::provider_name` gives that name, or "Gmail". A Microsoft account keeps "Outlook" or "Microsoft 365" in `accounts.provider_name`, from the tenant its sign-in named. _Avoid_: backend, service (which is a kind of work).

**App password**: a password a provider makes for one app from a page in the account's settings, used in place of the account's own password. Some providers, such as Fastmail and iCloud, always want one for IMAP; others only once two-step sign-in is on. The provider table says which, with the page that makes one, and Add Account says so under the password field and again when a login is refused. Penguin Mail keeps it in the keyring under `penguin-mail-imap`, keyed by the account's id, and never in the store; a Flatpak build keeps it in its own file through the Secret portal instead (`mailrs_gmail::secret_portal`). `mailrs_discover::PasswordKind`, `mailrs_sync::passwords`. _Avoid_: token, app-specific password.

**Tag**: a server mailbox a folder account keeps as a mark beside the one folder a message sits in: an Outlook category. A message carries any number of tags, adding or taking one never moves mail, and a move keeps them. `mailrs_domain::MailboxKind::Tag`, listed as `LabelKind::Tag`; `mailrs_store::labels::tag_ids` names an account's tags. _Avoid_: label (Gmail's), category (the inbox slices), colour.

**Focused Inbox**: Microsoft's split of an inbox into Focused and Other. Graph marks each message `focused` or `other`; the store keeps `other` as the category `FOCUS_OTHER`, so Other is the slice that has it and Focused the slice that lacks it, and both reuse the category bar, its counts and the listing. _Avoid_: priority inbox, important.

**Server mailbox**: a place a server files mail in: a Gmail label, later an IMAP or Outlook folder. It has the server's id, a name, a kind (system, label, folder, tag, or group: a folder that holds only other folders and no mail, as an IMAP server lists a `\Noselect` parent), sometimes a role, and a colour. `mailrs_domain::RemoteMailbox`, kept in the `mailboxes` table under an integer key. Not the sidebar's **Mailbox**, which may list a server mailbox, a search or a flag colour. _Avoid_: folder (which is Archive, Junk, Trash or All Mail), label outside Gmail's own words.

**Role**: what a server mailbox is for, whatever the server calls it: inbox, sent, drafts, trash, junk, archive, all or important. `mailrs_domain::Role`. Gmail's `INBOX`, `SENT`, `DRAFT`, `TRASH`, `SPAM` and `IMPORTANT` carry the roles; Gmail has no archive or all mailbox. Starred mail is a keyword, not a role. _Avoid_: special folder, system label (outside Gmail's own words).

**Keyword**: a mark a message carries that is not a place: `$seen`, `$flagged`, `$answered`, `$draft`, `$muted`, or any keyword a server stores. `mailrs_domain::mailbox::keyword`, kept in `message_keywords`. Gmail's `STARRED` and `MUTE` labels stand for `$flagged` and `$muted`, and its `UNREAD` label for the absence of `$seen`, so unread is kept as a fact derived from the keywords rather than as a row. _Avoid_: flag (which is the flag colour), tag.

**Membership**: one thing a message is in or carries: a server mailbox, a keyword or a category. `mailrs_domain::Membership`; everything one message holds is `Memberships`. A `MessageMeta` carries its memberships in `held` and the roles of its mailboxes in `roles`. `mailrs_gmail::labels` turns Gmail's labels into memberships and back. _Avoid_: label (outside Gmail), placement.

**Mail set**: which stored mail a list draws from: the mailbox with a role in each account (the inboxes), one server mailbox, the mail carrying a keyword (flagged, muted), unread mail, or one inbox category. `mailrs_domain::MailSet`. Thread lists, the sidebar's counts, triage and the rules name mail this way; only the Gmail adapter turns one into a label id. _Avoid_: label, filter, selector.

**Query tree**: a search in words every provider shares: sender, recipient, subject, words, a day range, days back from now, size, an attachment, unread, flagged, a mail set, or a mailbox by the name a person typed, joined by And, Or and Not. `mailrs_domain::query::Query`. Folders and smart mailboxes are query trees. The Gmail adapter prints one as Gmail search text with `mailrs_gmail::query::print`, `mailrs_domain::query::describe` prints one in plain English words for an account that reads no search syntax of its own, and the store runs one over its own copy of the mail with `mailrs_store::query::matching`, for a server that reads no Gmail syntax. What a person types into the search box stays in Gmail's operators (`SearchQuery::Native`); a Gmail account reads that text as it stands, and `mailrs_domain::query::parse` reads it as a tree for any other account. _Avoid_: filter, search string.

**Change set**: the one way stored mail changes: a list of changes (store a message, keep it under a new sync generation, add it to or take it out of a server mailbox, set a keyword or a category, delete a message or a thread, mark a thread whole) applied in one call inside the caller's transaction. It refreshes every thread row the changes touched and reports what each membership change did to each message, which is what Undo reverses. `mailrs_store::messages::apply`, taking `Change`s and answering `Touched`. _Avoid_: update, patch (which is the conversation page's word), batch.

**Listed**: whether a list shows a thread, kept on the thread's rows rather than worked out per query. A thread is listed in a server mailbox while one of its messages there sits outside the Trash and Spam (the mailbox itself aside, so the Trash lists trashed mail), and listed at all while any message of it sits outside both. `thread_mailboxes.listed`, `thread_categories.listed` and `threads.listed`, derived by the change set. The counts read the same rows, so a count and its list agree. _Avoid_: visible, hidden (for the column).

**Mail operation**: one change an action makes to messages, in words every server shares: file in a server mailbox, take out of one, move to the mailbox with a role, set a keyword or a category, or erase. `mailrs_sync::MailOp`. `ops_for` turns a triage action into operations for the account's capabilities (Archive on Gmail takes the inbox off; on a folder server it moves to the archive), the store applies them through the change set, and the backend sends them: the Google adapter as label changes, batched. A tag is a mark: adding or taking one never moves mail on a folder account, and a move keeps it (`ops::Tags`). _Avoid_: label delta, command.

**Moved from**: the place a person picked mail from when they moved it: the folder or role mailbox the list showed, in one account or in every account (the unified Inbox names each account's Inbox, the Remind Me list the Archive). On a folder account a whole conversation moved from there carries only its messages there. Mail from a search, a smart mailbox or a flag colour names no place, and neither does a thread with nothing left in it; then the roles decide, and copies in Sent, Drafts, Trash and Junk stay. `mailrs_sync::MovedFrom`, which `Mailbox::moved_from` gives for each mailbox and `MailActions::run_from` takes; an action that takes mail out of a place, such as removing a folder, names its own. _Avoid_: source, origin.

**Sync state**: where an account's mail backend left its feed of changes, in the backend's own words, kept as text in `accounts.sync_state` and read only by the adapter that wrote it. Gmail's is `{"history_id":N}`. `MailBackend::changes` takes one and answers what changed since, as gains and losses of memberships, with the state after; with none it answers where the feed stands now. A state the server no longer keeps, or cannot read, is `StateLost`, and the engine lists the mail again. `mailrs_sync::SyncState`. _Avoid_: cursor (which is also the backfill page token), history id (outside the Google adapter).

**Sync token** (DAV): where a CalDAV calendar or a CardDAV address book was when the app last read it, as the copy keeps it: `sync:` and the server's RFC 6578 token, or `ctag:` and the collection's getctag for a server without `sync-collection`, which is then read whole whenever its ctag moves. An address book's token holds one of these per book, as JSON. A token the server no longer takes reads the collection whole once. Not to be confused with **Sync state**, which is the mail feed's. _Avoid_: cursor, ctag (for the whole idea).

**Remote ref**: what the server calls a message now: Gmail's message id, or an IMAP location, the mailbox, its UIDVALIDITY and the UID (`mailrs_domain::Location`, written `<mailbox>/<uidvalidity>/<uid>`). The store keeps each message's in `remote_refs`, apart from its own id. An IMAP message's id is the location where the app first met it; a move rewrites the ref and leaves the id, so reminders, flags, the cached body and the open conversation keep their message. The engine hands the adapter each message's remote ref and reads the adapter's answers back into store ids (`mailrs_store::remote_refs`). A stored id whose ref now names another place is stale, and news naming it is dropped. For Gmail the two are the same and the engine reads no refs. Listings and searches answer them as `mailrs_sync::RemoteRef`. _Avoid_: server id, handle.

**Provider table**: the mail providers Penguin Mail knows without asking anyone: for each, its display name, its address domains, the MX hosts that mark a custom domain it hosts, its IMAP and SMTP servers, which password it takes, and the pages that make an app password and turn IMAP on. It also names providers the app cannot reach directly over IMAP (Tuta, HEY and Proton Mail). Proton Mail works through Bridge's local IMAP and SMTP servers when its certificate is pinned. The table also names the domains that belong to the Google or Microsoft sign-in. Compiled in from `discover/providers.toml`; `mailrs_discover`'s `table::Table`. _Avoid_: ISPDB (which is Mozilla's database, and only ever asked over the network), provider list.

**Discovery**: finding the mail servers for an address the person typed. The provider table answers by the exact domain with no network; otherwise the MX match, the domain's own autoconfig file, Mozilla's ISPDB, the MX host's settings, SRV records and a probe run side by side, and the highest-priority step that found something wins, each step dropped after 10 seconds. Only the address's domain goes out, and no name above it is ever built. `mailrs_discover::find`, answering a `Found`: a verdict and candidate servers, each marked with where it came from and whether the person must confirm its host names. _Avoid_: autodetect, autoconfig (which is one of its steps), Autodiscover (Microsoft's, which it never calls).

**Miss** (DAV): why the last search for an IMAP or POP3 account's CalDAV or CardDAV server found none: the server refused the login, the servers answered and none as a calendar or contacts server, or nothing answered. A search over several hints and user names keeps the strongest, a refused login first. `mailrs_store::services::Miss`, kept in `service_misses` and dropped once a server is found; Preferences words the account's Not Available line by it. _Avoid_: failure, error (a miss is the search's outcome, not one request's).

**Provider advice**: what Add Account's address page says about an address before Continue, from the provider table alone and with nothing sent anywhere: that the provider wants an app password, signs in through the browser, or lets no other mail app in. A provider tile picked on the first page shows its advice before any address is typed. `crate::add_account::post::advice`. _Avoid_: suggestion, which is the correction of a mistyped domain.

**IDLE connection**: the one IMAP connection per account that waits in IDLE (RFC 2177) on the mailbox the caller names, usually the Inbox, so the server reports new mail there as it arrives; a server without IDLE gets no such connection. The adapter ends the IDLE and issues it again every 25 minutes, and the engine keeps one watch across its polls. At most two more connections run sync and actions. `mailrs_imap::ImapClient::idle`. `MailBackend::watch` ends when the server reports a change, which wakes the engine's loop at once. A server that sends more during IDLE than the client takes loses the connection (`Woke::Dropped`); the engine syncs, and the next IDLE waits a minute, doubling at each drop in a row up to 15 minutes. Other mailboxes wait for the slow poll: every 5 minutes with the window open, every 15 with only the tray. A server without IDLE has its Inbox polled every minute. _Avoid_: push connection, listener.

**Next event card**: the card at the foot of the mail sidebar that names the next event on the calendars the person shows, from three hours before it starts, or the event under way until it ends unless another starts within a quarter of an hour. A click opens the event in the calendar. `mailrs::ui::calendar::next::next_up`. _Avoid_: agenda, upcoming widget.
